# Optional Delegation

Use this reference after project rules or the user explicitly enable delegation
preference, at non-trivial task start or when an independent subtask emerges.
RelayPact remains optional. ForgeRail guides the decision; RelayPact or the host
owns dispatch, model selection, concurrency, processes, wait, cancellation, retry
and recovery. Follow its current supported guidance for those operations; do not
copy its commands, add a scheduler, or create another task state system here.

## Confirm Preference, Capability And Scope

Use an existing project rule or explicit user instruction for preference. Do not
add a `.forgerail/config.json` field, another Profile, or a durable choice without
the existing adoption authority. Installation can justify suggesting adoption;
it does not enable delegation or authorize a task.

Resolve the currently discovered RelayPact Skill and supported entry point. Check
the actual execution route, executor availability, target/workspace requirements
and applicable authorization through that guidance. A file, historical receipt,
same-name Skill or tool listing alone does not prove execution works. Report
installation, current availability, actual invocation and accepted result
separately. Do not infer price or quality from a model name.

Reuse valid authorization for the same action, scope and target without asking
again for each delegation. Preference does not broaden task permissions, disclose
additional context, authorize remote delivery or bypass mandatory host limits.
Ask only for a material missing decision or authority after preparing the concrete
bounded choice. Continue independent authorized work when one route is blocked.

## Choose By Total Cost

Prefer the verified RelayPact route when the task has clear boundaries, small
transferable input, independently verifiable output, and reasonable expected
total cost: decomposition, handoff, execution, review and rework. Keep goal
ownership, architecture trade-offs, integration and acceptance with the Host.

| Situation | Host judgment |
| --- | --- |
| Targeted investigation, bounded test addition, documentation synchronization or independent review with explicit inputs and checks | Prefer delegation when the full cost is justified and authorization covers it |
| A few direct steps, full-conversation dependence, tightly coupled edits, or handoff/review cost exceeding benefit | Handle directly and briefly state the concrete reason |
| Only installation is known, executor is unavailable, or the supported route cannot be verified | Continue work the Host can complete; report the capability gap without blocking on RelayPact |

Do not delegate merely to reduce Host output tokens. When evaluating a real task,
report observable elapsed time, available usage/cost and review or rework, plus a
reasonable direct-handling comparison. Mark unavailable measurements unknown;
without comparable evidence do not claim savings, speed or quality gains.

## Hand Off, Collect And Accept

Reuse the [Task Envelope and Return Contract](contracts.md). Give only the context
and dependencies required to finish the subtask: goal, owner/target, allowed
scope, prohibited actions, deliverables and acceptance checks. Avoid copying the
whole conversation. Require completion, evidence, incomplete work, blockers and
any need for user input to return to the main Host.

Record the delegated identifier in the existing task context and use the
supported wait or monitoring mechanism to collect completion or attention-required
state before closing the main task. Do not invent cross-task notifications. If
the host cannot wake an ended main task, explain that limit and provide a
deterministic follow-up check. These are handoff notes, not a new persistent ledger.

Inspect the actual artifacts, diff, relevant checks and evidence against the
acceptance criteria. Do not accept an executor's success claim as proof or repeat
all its work indiscriminately. Resolve blocking findings within authorized scope,
integrate accepted output, and report status, changes/findings, validation,
blockers and the next action in the main task. The Host owns the final result.

On failure, interruption or partial evidence, preserve observable state using the
tool's supported mechanism. Report incomplete and unchecked work; do not claim
success, silently switch execution routes or blindly start duplicate workers.
Follow RelayPact/host instructions for recovery and reuse still-valid authority.
Delegated execution never grants merge, release, publish, deletion or broader scope.
