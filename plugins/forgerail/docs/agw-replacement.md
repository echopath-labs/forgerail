# AGW replacement qualification

[0.1.0](release-0.1.0.md) retains the self-contained AGW/WHR guidance and prior explicit-source behavior evidence, with additional project snapshot adoption, workflow checks, rollback and fresh-session handoff validation. Native Plugin activation, strict session isolation and project-specific legacy consumers remain outside that evidence; qualify each project before replacing its existing activation.

## What complete replacement means

With legacy AGW and WHR absent from the Agent's available inputs, the main
ForgeRail Plugin plus the project's existing instructions must preserve the
baseline workflow and health behavior. Equivalent behavior does not require
identical wording or CLI enforcement of every natural-language rule. It does
require that every duty has a reachable owner, and that real tasks preserve
scope, authorization, records, evidence and recovery.

The main Plugin owns baseline Git discipline, durable records and indexes,
impact review, authorization, stage summaries, handoff, optional structured
exchange and independent WHR. Project-specific branch, validation, business and
delivery rules remain in the project. External Packs deepen release, Rulesets,
thread closure or multi-owner coordination; they are not needed to recover the
old baseline runbook check or ordinary task completion.

See the [behavior inventory](agw-replacement-coverage.json). Structural checks
verify reachable packaged references; they cannot certify Agent compliance.
The old [coverage baseline](agw-coverage-baseline.json) and shadow phrase checks
are historical architecture evidence, not a current project migration verdict.

## Qualification gates

1. Freeze the actual installed AGW/WHR files, versions when available, content
   digests and activation locations. Separate project extensions from portable
   rules. A product's frozen version alone does not qualify every local copy.
2. Review each behavior's self-contained ForgeRail owner and loading trigger.
   Retain an explicit disposition for changed defaults and consumer formats.
3. Verify all references in the packed main Plugin without legacy files or
   sibling Packs. Broken loading paths block content readiness.
4. Execute the [behavior scenarios](agw-replacement-validation.md) in isolated
   host tasks. Capture exact provider discovery, inputs, permitted actions,
   before/after state and actual results. Independent review checks the evidence.
5. Bind passed evidence to an immutable successor release and documented host
   configuration. A changed candidate requires relevant evidence to be renewed.
6. Apply a separately approved project adoption plan; verify a fresh task and
   rollback. Leave other projects on AGW until their own baseline is qualified.

Legacy repository archive, redirect, deprecation and deletion are independent
lifecycle decisions. They are not prerequisites to one project's functional
replacement and never follow automatically from test or migration success.

## Installation and portable project adoption

Follow the [npm installation guide](installation.md), then explicitly load the installed Skill in a fresh Agent task. Machine installation is not tracked by a project clone. Do not copy the Plugin or add npm dependencies to every child repository.

Before switching activation, write the approved exact version and setup/discovery
instructions in the existing project onboarding system. Record the expected four
main Skills and use the exact identity returned by the host. Codex release
evidence has shown `forgerail:forgerail`,
`forgerail:forgerail-workspace-diagnosis`,
`forgerail:workspace-health-review` and
`forgerail:architecture-convergence-audit`; verify the current host instead of
guessing a short-name resolution order. Do not claim that this historical
discovery proves native activation. The npm route uses explicit loading of the installed Skill paths.

Keep shared workspace policy at its owner and each independent project's
development, records and deployment policy in that project. A standalone clone
or externally located worktree must carry or explicitly recover every required
policy; do not assume its old parent AGENTS.md is loaded. Do not assume nested
Skills are discovered from the coordination root. Test root, child, standalone
clone and external worktree entry points separately. Platform-specific support,
including Windows, remains unknown until evidence is available.

Switch only the agreed activation entries for the selected project. Preserve
unrelated instructions and make the choice of workflow and WHR providers explicit.
Do not silently select AGW when ForgeRail is missing, or execute both. Report the
missing dependency before governed engineering work, use the documented setup
route, or restore the approved old activation. An inactive rollback copy must
not remain in an auto-discovery location that reactivates it.

Single-host adoption may use a managed block; multiple hosts may use FORGERAIL.md
and thin bindings. Neither is needed just to evaluate capability. The adoption
planner is not an AGW migration engine: it does not remove old activation rules,
resolve Skill collisions or prove complete inherited-policy recovery. Those
changes need their own exact reviewed migration diff and host verification.

## Rollback

Before migration, preserve the exact old activation files, Skill baseline and
digests in the project's existing recovery system, outside automatic discovery
when necessary. Record the active owner and qualified Plugin version. On failed
verification, restore only the approved paths after checking concurrent edits;
re-discover the old owner in a new task. Do not delete code, records, Git history,
user changes or unrelated Plugin registrations. If the same marketplace supplies
other Plugins, do not remove it blindly. Uninstalling a Plugin does not remove
project bindings. Compare before/after state rather than requiring an initially
dirty project to become clean.

Ordinary results remain human-readable. Envelopes and receipts can reuse the
conversation and existing project records; migration does not introduce a second
record system. Optional old-format exchange retains field meaning, reports the
actual ForgeRail provider and requires consumer compatibility validation.
